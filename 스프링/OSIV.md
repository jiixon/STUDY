### **OSIV (Open Session In View)**

- JPA에서 **데이터베이스 커넥션과 영속성 컨텍스트의 생명주기를 관리**하는 전략이다.
- 기본값은 True로 아무런 설정을 하지 않는다면 OSIV 옵션은 켜져있는 상태이다.

### OSIV : true

- DB 트랜잭션을 시작할 때 JPA 영속성 컨텍스트가 DB 커넥션을 가져옴
- OSIV가 켜져있으면 @Transactional 메서드를 벗어나도 커넥션을 계속 유지
    - API 응답이 나가고 화면이 렌더링 될 때까지 영속성 컨텍스트를 유지
- 그래서 View Template이나 Controller 단에서도 Lazy 로딩 가능
    - Lazy 로딩: 영속성 컨텍스트가 살아 있어야 가능
- 너무 오랫동안 DB 커넥션을 사용하기 때문에 실시간 트래픽이 중요한 애플리케이션에서는 커넥션이 모자르는 문제 발생 → 장애로 이어짐ㅇ
- 단점: 로직 상에서 외부 API를 호출한다면 이걸 처리하는 시간만큼 커넥션 리소스를 반환하지 못함
- 장점: 지연 로딩을 적극 활용할 수 있음!
- **application.yml** (OSIV설정)
    - default이므로 따로 설정해주지 않아도 된다.

### OSIV : false

- 트랜잭션으로 가져온 데이터를 요청한 지점에서 반환한 다음엔 DB 커넥션을 쓰지 않음
    - 사용자 요청이 많을 경우 유연하게 사용할 수 있음
- 모든 지연 로딩을 트랜잭션 안에서 해결해야 함
    - 지연 로딩을 하려면 영속성 컨텍스트가 살아있어야 함
    - 지금까지 구현한 많은 지연 로딩 코드를 트랜잭션 안으로 넣어줘야 함
    - 따라서 트랜잭션이 끝나기 전에 지연 로딩을 강제로 호출해두거나 fetch join을 사용
- 트랜잭션이 종료(함수가 종료)되는 시점에 영속성 컨텍스트는 닫히고 데이터베이스 커넥션은 반환된다.
- yml에서 요렇게 사용하면 됩니당

### 그래서 true? false? 뭐가 좋은가요

- OSIV 전략을 사용하는 경우
    - 지연로딩이 controller와 view 단에서 가능함
    - 단, 지연로딩을 트랜잭션 내에 모두 처리해야한다면,
        - 코드 복잡도도 올라고, 유지보수 측면도 좋지 않음
    - 트래픽 적은 경우 전략을 사용하는것도 좋다!
- OSIV 전략을 사용하지 않는 경우
    - 데이터 커넥션 리소스 낭비를 막을 수 있음

→ 애플리케이션의 요구 사항과 성능 목표를 고려해서 적절하게 사용해야함!
