### 엔티티 매핑 어노테이션

- 객체 - Table 매핑**:** `@Entity`, `@Table`
- field - column 매핑: `@Column`
- 기본 키 매핑: `@Id`, `@GeneratedValue`
- 연관 관계 매핑: `@ManyToOne`, `@OneToMany`, `@ManyToOne`

### 객체 - Table 매핑

**@Entity**

- 해당 클래스는 JPA가 관ㄹ
- 기본 생성자 필수
    - 파라미터 없는 public 또는 protected 새엇아
- 사용할 수 없는 클래스 목록
    - final 클래스, enum, interface, inner 클래스
- 저장할 필드에 final 사용 불가
- name 속성 사용하여 JPA 에서 사용할 엔티티 이름 지정 가능
    - ex. `@Entity(name = "hello")`

<aside>
💡

- `@NoArgsConstructor`
    - 파라미터가 없는 디폴트 생성자를 생성 (기본 생성자)
- `@AllArgsConstructor`
    - 모든 필드 값을 파라미터로 받는 생성자를 생성
- `@RequiredArgsConstructor`
    - final이나 @NonNull으로 선언된 필드만을 파라미터로 받는 생성자를 생성
</aside>

**@Table**

- 엔티티와 매핑할 DB 테이블 지정
- `@Table` 없으면 `@Entity`의 이름 따라 테이블 매핑
- 속성 정리
    - `name` : 매핑할 테이블 이름
    - `catalog` : DB의 catalog 매핑
    - `schema` : DB의 schema 매핑
    - `uniqueConstraints` : DDL 생성 시 유니트 제약 조건 생성

### 데이터베이스 스키마 자동생성

- DDL은 애플리케이션 실행 시점에 자동생성
- 테이블 중심 → 객체 중심
- 데이터베이스에 맞는 적절한 DDL 생성
    - 생성된 DDL은 개발 장비에서만 사용
- 생성된 DDL 은 운영서버에서 사용하지 않거나, 적절히 다듬은 후 사용
- 속성
    - hibernate.hbm2ddl.auto
    - `create` : 기존 테이블 삭제 후 다시 생성 (DROP + CREATE)
    - `create-drop` : create 와 같으나 종료시점에 테이블 DROP
    - `update` : 변경분만 반영(운영DB에는 사용하면 안됨)
        - 추가만 가능, 삭제는 반영 X
    - `validate` : 엔티티와 테이블이 정상 매핑되어있는지만 확인
    - `none` : 사용하지 않음
- 주의
    - 운영 장비에는 절대 create, create-drop, update 사용X
    - 개발 초기 단계 create, update
    - 테스트 서버 update, validate
    - 스테이징과 운영서버 validate, none

### field - column 매핑

- 사용 어노테이션
    - `@Column`, `@Temporal`, `@Enumerated`, `@Lob`, `@Transient`

**@Column**

```java
@Column(name = "username")
private String name;
```

- name
    - 필드와 매핑할 테이블의 컬럼 이름
    - 기본값 : 객체 필드 이름
- insertable, updateable
    - 등록, 변경 가능 여부
    - false로 설정 시 등록, 변경 불가
    - 기본값 true
- nullable(DDL)
    - null 값 허용 여부
    - false로 설정 시 DDL 생성 시에 not null 제약 조건 붙음
    - 기본값 true
- unique(DDL)
    - `@Table`의 `uniqueConstraints` 속성과 같지만 단일 컬럼에만 적용 가능
    - DDL 생성 시 유니크 제약조건 이름 랜덤으로 설정
    - 기본값 false
- columnDefinition
    - DB의 컬럼 정보 직접 줄 수 있음
    - ex. `colmunDefinition=”varchar(100) default EMPTY”`
- length(DDL)
    - 문자 길이 제약 조건
    - String 타입에만 사용 가능
- precision, scale(DDL)
    - 아주 큰 숫자나 정밀한 소수 다룰 때 사용
    - BigDecimal, BigInteger 사용 가능
    - double, float 타입 적용 X
    - percision: 소수점을 포함한 전체 자릿수
    - scale:소수의 자리수
    - ex. `@Column(precisioin=0)`

<aside>
💡

SQL : 데이터베이스에서 구조화된 질의 언어

종류 - DDL, DML, DCL, TCL

**DDL(Data Definition Language, 데이터 정의어)**
- 테이블이나 컬럼 등을 생성, 수정, 삭제

`CREATE` : 새로운 테이블 생성
`ALTER` : 기존 테이블 구조 변경
`DROP` : 기존 테이블 삭제
`TRUNCATE` : 기존 테이블 초기화
`RENAME` : 기존 테이블 이름 변경

**DML(Data Manipulation Language, 데이터 조작어)**
- 테이블의 데이터를 조회, 저장 수정, 삭제

`SELECT` : 저장된 데이터를 조회
`INSERT` : 새로운 데이터를 저장
`UPDATE` : 저장된 데이터를 수정
`DELETE` : 저장된 데이터를 삭제

**DCL(Data Control Language, 데이터 제어어)**
- 데이터에 대한 접근 권한 제어로 권한을 부여, 회수

`GRANT` : 유저에게 권한 부여
`REVOKE` : 유저로부터 권한 회수

**TCL(Transaction Control Language, 트랜잭션 제어어)**
- 트랜잭션 컨트롤하는 명령어(DCL로 구분하기도 함)

`COMMIT` : 올바르게 완료한 작업으로 인한 데이터를 데이터베이스에 영구적으로 반영
`ROLLBACK` : 작업 시작 이전의 상태로 되돌림
`SAVEPOINT` : 저장점을 지정, 이후 ROLLBACK과 함께 사용하여 특정 지점까지 ROLLBACK이 가능

</aside>

### BigDecimal

double, float의 소수점을 정밀도가 완벽하지 않아 값의 오차 발생, 내부적으로 수를 저장할 때 이진수의 근사치를 저장하기 때문

기본적으로 BigDecimal은 문자열 → 사칙연산 불가능

- BigDecimal 선언
    - `BigDecimal bd1 = new BigDecimal(”123.12345”);`
- BigDecimal 연산
    - `add()` : 더하기
        - ex. bd1.add(bd2);
    - `substract()` : 빼기
    - `multiply()` : 곱하기
    - `divide()` : 나누기
    - `remainder()` : 나머지
- BigDecimal 타입변환
    - → String : `bd.toString()`
    - → int : `bd.intValue()`
    - → long : `bd.longValue()`
    - → float : `bd.floatValue()`
    - → double : `bd.doubleValue()`
- BigDecimal 비교
    - `compareTo`
</aside>

**@Enumerated**

- enum 타입 매핑할 때 사용

    ```java
    @Enumerated(value = EnumType.STRING)
    private Location location;
    ```

- DB에 저장 시 타입 선택 가능
    - enum 순서(int) 또는 enum 이름(string)
- 속성
    - value
        - `EnumType.ORDINAL`: enum 순서 저장(int) - 기본값
        - `EnumType.STRING`: enum 이름 저장(string)

**@Tempoarl**

- 날짜 타입 매핑할 때 사용
    - LocalDate, LocalDateTime을 사용할 때 생략 가능

    ```java
    @Temporal(TemporalType.TIMESTAMP)
    private Date createdDate;
    
    //@Temporal 생략 가능
    private LocalDate createDate2
    ```


**@Lob**

- 대형 오브젝트 저장할 때 사용

    ```java
    @Lob
    private String description;
    ```

- 속성X
- DB의 BLOB, CLOB 타입과 매핑
    - CLOB: String, char[], jata.sql.CLOB
    - BOLB: byte[], java.sql.BLOB

<aside>
💡

JPA의 두가지 접근 방식
- 엔티티의 필드나 메서드(주로 getter)를 통해 데이터를 읽음

1. 필드(Field)방식
    1. `@Id` 가 필으데 붙으면 JPA는 해당 클래스의 필드에 직접 접그해서 값을 읽고 씀
2. 프로퍼티(Property) 접근 방식
    1. `@Id`가 getter 메서드에 붙으면 JPA는 해당 클래스의 getter 메서드를 호출해서 값을 읽고 씀

주의할 점

- 한 엔티티 클래스에서 필드 방식과 프로퍼티 방식 혼용 X
    - JPA 2.0부터는 `@Access`로 명시하면 가능
- 즉, `@Id` 가 필드에 있으면 다른 매핑 애노테이션도 전부 필드에 붙어야 함
</aside>

**@Transient**

- 필드

    ```java
    @Transient
    private Integer temp;
    ```

    - 매핑X
        - 엔티티 객체의 데이터와 테이블 컬럼과 매핑하고 있는 관계를 제외하기 위해 사용
        - 정확하게는, 영속 대상에 제외 시키기 위해 사용
    - DB에 저장X, 조회X
    - DDL 자동 생성 과정에서 해당 컬럼 제외하고 테이블을 구넝
- 메서드
    - setter 메서드가 아닌 getter 메서드에 애노테이션을 선언해주어야함

    ```java
    @Entity
    public class Member{
        @Id //필드 방식
        private Long id; 
        private String userId;
        private String password;
        private String confirmPassword;
        
        @Transient
        public String getComfirmPassword(){ return this.confirmPassword; }
    }
    ```

    - 위와 같이 했을 때 기대하는 결과
        - 테이블 컬럼 생성 및 CRUD SQL문 대상 컬럼 제외
    - 실제 동작
        - confirmPassword 영속 대상에서 제외되지 않음
    - 이유
        - @Id 애노테이션의 위치가 필드에 있으므로 해당 코드는 필드 접근방식을 따르고 있음
        - `@Transient` 를 메서드에 붙였기 때문에 JPA가 무시
        - `confirmPassword` 는 여전히 영속성 대상
        - 해결 방법?

            ```java
            @Entity
            public class Member {
            
                @Id  // 필드 접근 방식
                private Long id;
            
                @Transient  // 필드에 붙임
                private String confirmPassword;
            
                public String getConfirmPassword() {
                    return confirmPassword;
                }
            }
            ```

            - 필드에 붙이자
    - 즉, `@Transient` 를 메서드에 붙였다면, 프로퍼티 접근 방식일 때만 유효

### 기본키 매핑

**@Id**

- 직접 할당
- @Id 만 사용

**@GeneratedValue**

```java
@Entity
public class Member {
	
		@Id
		@GeneratedValue(strategy = GenerationType.*IDENTITY*)
		private Long id;
}
```

- 자동생성
- 전략
    - IDENTITY
        - 기본 키 생성을 데이터베이스에 위임
        - 주로 MySQL, PostgreSQL, SQL Server, DB2에서 사용
            - ex. MySQL의 AUTO_INCREMENT
        - JPA는 보통 트랜잭션 커밋 시점에 INSERT SQL 실행
        - AUTO_INCREMENT는 데이터베이스에 INSERT SQL 실행한 이후에 ID 값을 알 수 있음
        - em.persist() 시점에 즉시 INSERT SQL 실행하고 DB에서 식별자를 조회
    - SEQUENCE
        - 유일한 값을 순서대로 생성하는 특별한 데이터베이스 오브젝트(ex.오라클 시퀀스)
        - 오라클, PostgreSQL, DB2, H2 데이터베이스에서 사용
        - 사용법

            ```java
            @Entity
            @SequenceGenerator(
            				name = "MEMBER_SEQ_GENERATOR",
            				sequenceName = "MEMBER_SEQ", //매핑할 데이터베이스 시퀀스 이름
            				initialValue = 1, allocationSize = 1)
            public class Member {
            	
            		@Id
            		@GeneratedValue(strategy = GenerationType.SEQUENCE,
            						generator = "MEMBER_SEQ_GENERATOR")
            		private Long id;
            }
            ```

    - TABLE
        - 키 생성 전용 테이블을 하나 만들어서 데이터베이스 시퀀스를 흉내내는 전략
        - 장점 : 모든 데이터베이스에 적용 가능
        - 단점 : 성능

권장하는 식별자 전략

- 기본 키 제약 조건 : null 아님, 유일, 변하면 안된다.
- 대리키(대체키)를 사용
    - 미래까지 이 조건을 만족하는 자연키를 찾기 어려움
- 권장
    - Long 형 + 대체키 + 키 생성전략 사용
