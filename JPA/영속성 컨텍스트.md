### 영속성 컨텍스트란?

- 엔티티를 영구 저장하는 환경
- EntityManager.persist(entity);
    - 엔티티를 영속성 컨텍스트에 저장한다는 뜻
- 엔티티 매니저를 통해서 영속성 컨텍스트에 접근

엔티티의 생명주기

- 비영속(new/transient)
    - 영속성 컨텍스트와 전혀 관계가 없는 새로운 상태
- 영속(managed)
    - 영속성 컨텍스트에 관리되는 상태
- 준영속(detached)
    - 영속성 컨텍스트에 저장되었다가 분리된 상태
- 삭제(removed)
    - 삭제된 상태

![영속성 컨텍스트](/JPA/images/img1.png)

비영속
- 객체를 생성한 상태
- 영속 컨텍스트(entityManager)에 아무것도 있지 않음

```java
//비영속
Member member = new Member();
member.setId("member1");
member.setUsername("회원1");
```

영속

- 객체를 저장한 상태

```java
EntityManager em = emf.createEntityManager();
em.getTrasaction().begin();

//객체를 저장한 상태(영속)
em.persist(member); 
```

- 이때, DB에 저장된 것은 아님, 이후에 커밋해야 저장

준영속, 삭제

```java
//회원 엔티티를 영속성 컨텍스츠에서 분리(준영속)
em.detach(member);

//객체를 삭제한 상태(삭제)
em.remove(member);
```

영속성 컨텍스트의 이점

- 1차 캐시
- 동일성(identity) 보장
- 트랜잭션을 지원하는 쓰기 지연 (transactional write-behind)
- 변경 감지(Dirty Checking)
- 지연 로딩(Lazy Loading)

1. 1차 캐시
    - 영속성 컨텍스트에 1차 캐시 존재
    - 캐시는 map 형태로 key-value 저장
        - key: DB의 PK(기본키)
        - value: 객체
    - 동작 예시
        - mmeber1이 PK가 member1인 엔티티 생성 후 영속화
        - 다음 PK가 member1인 엔티티를 조회하면?
            - em.find(Member.class, “member1”);
            - JPA는 영속성 컨텍스트에 1차 캐시 확인
            - key = member1 있으면 캐시에서 값 가져옴
        - 만약 1차 캐시에 찾는 엔티티가 없으면?
            - DB 조회
            - DB에 데이터 있으면 가져와 1차 캐시에 저장후 데이터 반환

        > 💡 사실, 1차 캐시는 큰 도움이 되진 않는다.
        > 1. 1차 캐시가 있는 EntityManager는 트랜잭션 단위를 만들고 사라짐, 1차 캐시가 살아있는 시간은 매우 짧아 성능에 큰 효과는 없음
        > 2. 트랜잭션마다 각자 EntityManager를 사용, 각자 다른 영속성 컨텍스트와 1차 캐시를 가짐

2. 동일성 보장
    - 같은 트랜잭션 안에서 같은 객체는 == 비교 보장

3. 트랜잭션을 지원하는 쓰기 지연
    - 한 트랜잭션 안에서 DB에 보낼 쿼리문을 모았다가 한번에 보냄
    - 쿼리문 모아두는 곳 : 쓰기 지연 SQL 저장소(in 영속성 컨텍스트)
    - 쿼리문 보내는 시점
        1. 트랜잭션 끝나기 전 - transaction.commit()
        2. EntityManager 플러시 - em.flush()
    - 네트워크 부하를 줄이기 위한 기능
    - em.persist(entity)를 하면?
        - 영속성 컨텍스트 1차 캐시에 저장
        - JPA가 엔티티 분석하여 INSERT 쿼리 생성하여 쓰기 지연 SQL 저장소에 쌓아둠
    - 예시

      ![영속성 컨텍스트](/JPA/images/img2.png)

        - 각 memberA, memberB 객체 생성 후 영속화
        - 1차 캐시에 저장 및 INSERT 쿼리 쌓아둠

      ![영속성 컨텍스트](/JPA/images/img3.png)

        - 이때, transaction.commit() 을 하게 된다면?
        - 커밋 시점에 EntityManager 에서 flush() 호출
            - flush : 영속성 컨텍스트의 내용을 DB에 반영, 모아두었던 SQL에 날라감
        - 이후 실제 데이터 저장
    - 버퍼링 기능
        - 모아두었다가 쿼리 한번에 보낼 수 있음
        - Hibernate 경우 옵션 부여 가능
            - `hibernate.jdbc.batch.size`
            - 지정한 사이즈 만큼 모아서 DB에 한번에 쿼리를 보내고 commit 하는 기능
            - ID 전략이 IDENTITY일 경우 배치 불가
                - `@GeneratedValue(strategy = GenerationType.IDENTITY)`
                - INSERT 즉시 DB 호출이 필요해서 배치가 불가능
                - `SEQUENCE`나 `TABLE` 전략 사용 권장
4. 변경 감지(Dirty Checking)
    - 영속성 컨텍스트에서 보관하는 데이터에 변경이 일어났는지 확인
    - 데이터 변경이 일어났다면?
        - JPA가 UPDATE 쿼리문 날려줌
        - 즉, 값 변경 후 update 쿼리문을 날릴 코드 필요X
    - 작동 순서

      ![영속성 컨텍스트](/JPA/images/img4.png)

        - 트랜잭션 커밋이 발생하면
        1. flush() 호출
        2. 1차 캐시에서 entity와 스냅샷 비교
            1. 스냅샷: 최초로 영속성 컨텍스트에 들어온 객체 상태
            2. entity: 실제 값
        3. entity와 스냅샷이 다르다면 쓰기지연 SQL 저장소에 update 쿼리문 추가
        4. DB에 update 쿼리문 반영 후 commit
    - 예시

        ```java
        Member member = em.find(Member.class, 150L);
        Mmember.setName("newName");
        
        tx.commit();
        ```

        - ID가 `150L` 인 Member를 찾고 setName()으로 데이터 변경
        - `em.persist()`를 하지 않아도 자동으로 update 쿼리 나감


> 💡추가 
> 엔티티 삭제 → `em.remove(entity);`
> 위 예시 update와 동일한 방법으로 commit 시점에 delete 문이 DB로 날아가 적용

5. 지연 로딩
    - 엔티티를 DB에서 가져올 때 만약 연관관계를 가진 다른 객체를 가지고 있다면?
        - 즉시 로딩 : 엔티티 조회할 때 연관된 객체도 함께 DB에서 조회
        - 지연 로딩 : 연관된 객체는 조회X, 나중에 필요하면 그 때 DB에서 가져옴
    - 각 연관 관계마다 즉시 로딩, 지연 로딩 설정 가능
